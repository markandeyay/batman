# Spikes S5 and S6: shared-pool registration and the probe line

Run on 2026-10-10 (23:11 to 23:13 UTC) against the real Batman project (shared pool, free tier) and the probe project ed2b4211-... (shared pool, free tier).
Script: `scripts/spike-probe.ts` (`npx tsx scripts/spike-probe.ts list|run|cleanup [--yes]`, or `pnpm spike probe run`). Helper: `apps/probe/src/register.ts`.
All phone numbers are redacted to the last 4 digits. No message was sent to, and no registration was made for, HUMAN_IPHONE_E164 or TEST_GUARDIAN_E164 (the script refuses both). Only Photon pool numbers were targeted.

## Ordering procedure tried

The probe has no number until it has a user. Instead of registering the human's iPhone on the probe project (the brief's suggested seed), the script seeded with Batman's own pool number, so no real person was involved at any step.

1. Probe registers BATMAN_LINE_E164 (***5362). Probe gets assigned ***5365 (not equal to BATMAN_LINE).
2. S5: Batman sends to ***5365 while it is not a Batman user (below).
3. Batman registers ***5365. Batman gets assigned ***7754, **not** ***5362. So Batman would text the probe from a different line than the one the probe texts.
4. The first run then iterated toward a fixed point (Batman user P -> B, probe user B -> P):

```
ORDER step 1: probe registers ***5362 -> assigned=***5365 created=true equalsBatmanLine=false
ORDER iter 1a: batman registers ***5365 -> assigned=***7754 created=true equalsBatmanLine=false
ORDER iter 1b: probe registers ***7754 -> assigned=***0754 created=true sameAsBefore=false
ORDER iter 2a: batman registers ***0754 -> assigned=***9185 created=true
ORDER iter 2b: probe registers ***9185 -> assigned=***7665 created=true
ORDER iter 3a: batman registers ***7665 -> assigned=***2852 created=true
ORDER iter 3b: probe registers ***2852 -> assigned=***1756 created=true
fatal: no fixed point after 3 iterations; pool keeps assigning new numbers
```

Every registration of a new user returned a new, distinct pool number (4 users on each project, 4 distinct assigned numbers each). A reciprocal pair never forms. The iteration was removed from the script so re-runs are idempotent and create no users. Because no reciprocal pair exists, `PROBE_LINE_E164` and `BATMAN_LINE_FOR_PROBE_E164` were **not** written to .env (writing a non-reciprocal pair would mislead later code; `run --write-env` forces it).

Even a reciprocal pair would not help, because of the S6 finding below.

## S5: send to a number that is not a project user

```
S5 availability on Batman for ***5365: HTTP 200 {"succeed":true,"data":{"available":true}}
S5 Batman messages.sendText(any;-;***5365, "batman s5 unregistered ...") with ***5365 unregistered on Batman
S5 result: ERROR ValidationError grpc=3 INVALID_ARGUMENT code=internalError retryable=false
  message="[spectrum-imessage] Target is a Photon-managed shared line, not a valid recipient. Send to the user's own number, not the assigned line."
```

- The only unregistered numbers this spike may message are pool numbers, and Photon rejects pool numbers as recipients before any user check. So the real S5 question (an unregistered real phone, like a new guardian) could not be tested without a consenting non-pool number.
- Stable docs (llms-full.txt 4823 to 4826, PHOTON_NOTES mismatch 5): a shared line only messages recipients registered as project users; anything else fails with `Target not allowed for this project`.
- **Conclusion: guardians must be registered (`POST /projects/{id}/users/`, `type: "shared"`) before Batman can text them.** Registration itself is a management call and sends nothing.
- `GET /imessage/shared/availability` returned `available: true` for a Photon pool line, so it cannot detect pool lines.
- Each user gets their own pool number. The guardian will see a different number than the user's Batman number (here the human's iPhone sees ***5362; every later user got a different line). Templates must not tell the guardian "this is the number your friend uses".

Optional later confirmation (needs the human): with a consenting real number that is not registered, send once and record the exact error, then register and resend.

## S6: probe <-> Batman over real iMessage

Second run, after registrations existed (probe user ***5362 -> ***5365; Batman user ***5365 -> ***7754). Probe sends used spectrum-ts `imessage(app).space.create(BATMAN_LINE).send(text)`; Batman sends used gRPC `messages.sendText("any;-;" + probe)` (what spectrum-ts does in shared mode); Batman reads used `messages.listInChat`; the probe read its own `app.messages` stream. The Batman `app.messages` stream was never iterated.

```

S6 round 1 batman->probe: FAIL; send error (same ValidationError)
S6 round 2 probe->batman: FAIL; (same)
S6 round 2 batman->probe: FAIL; (same)
S6 round 3 probe->batman: FAIL; (same)
S6 round 3 batman->probe: FAIL; (same)

SUMMARY S6: FAIL rounds=[{"i":1,"p2bMs":null,"b2pMs":null},{"i":2,...},{"i":3,...}]
```

Registration does not lift the block: both targets were registered users on the sending project. `listInChat` on a pool-line chat is rejected too. Two shared-pool projects cannot text each other.

## Side effects to clean up

The first run created 7 users whose phone number is a pool line (Batman: ***5365, ***0754, ***7665; probe: ***5362, ***7754, ***9185, ***2852). They can never receive messages and they count toward the free tier's `maxSharedUsers`, which guardians also need. `npx tsx scripts/spike-probe.ts cleanup` lists them (dry run, verified it skips the human's user ***8747); `cleanup --yes` deletes them with `DELETE /projects/{id}/users/{userId}/`. Not run yet; needs the main conversation's go-ahead.

## Recommendations

1. **apps/probe:** do not build the probe E2E runner on two shared-pool projects. Use the documented fallback (`pnpm chat`, sim, guided iPhone session 16.4) and mark the `pnpm e2e:probe` exit criterion as "documented S6 fallback".
2. A probe only becomes possible if at least the receiving side is not a shared pool line. Ask Photon (Discord, spec 20) whether a Business dedicated line can text, or be texted by, another project's dedicated line, or whether a sandbox/test recipient exists. Until then, treat it as unavailable.
3. Keep `apps/probe/src/register.ts` as the shared registration helper (`registerUser`, `ensureUser`, `listUsers`, `deleteUser`); move or copy it into the server gateway for guardian onboarding and `scripts/admin-add-user.ts` (spec 11.1). Guardian onboarding must call `ensureUser` before the first guardian text and store the returned `assignedPhoneNumber` per guardian.
4. Gateway error mapping: `ValidationError` (gRPC 3) with `retryable=false` and code `internalError` is the shape for both "Photon-managed shared line" and (per docs) "Target not allowed". Never retry it; for a guardian, register then retry once.
5. Update PHOTON_NOTES (mismatch 5) with the observed pool-line error text and that `availability` returns true for pool lines.
